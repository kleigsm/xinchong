## D-001 多端策略：桌面优先，小程序延后（2026-11-03 · 已定）

**背景**：微信小程序做不到桌面悬浮，而「桌面常驻」是芯宠的全部差异化。

**选项**：A 形象生成器 / B 窗口内桌宠 / C 素材云同步 / D 不做

**决定**：只做 A 类，且必须等桌面版有留存数据之后。

**理由**：B 类会滑向聊天与养成，与 Won't 冲突；A 类手机拍照体验优于 PC，且能作为官网引流入口。

**代价**：放弃「多端覆盖」的叙事，答辩时少一个亮点。

**复审**：桌面 MVP 上线并有留存数据后；或微信类目准入确认可做。

## D-002 仓库根目录即客户端工程根目录（2026-11-03 · 已定）

**背景**：产品仓库只有一个应用，不需要 monorepo。

**选项**：A 根目录放工程 / B `client/` 子目录 / C pnpm workspace

**决定**：A。`package.json` 放仓库根。

**理由**：少一层路径，Electron 打包工具和 IDE 都默认从根找 `package.json`；`client/` 子目录会让 `electron-builder`、`tsconfig`、CI 全部多一层无谓配置。

**代价**：以后若真要做小程序，需要另开仓库（本就如此，见 D-001）。

**复审**：若同仓库出现第二个可执行应用。

## D-003 文档即状态：STATUS + 日志 + BACKLOG（2026-11-03 · 已定）

**背景**：多人协作 + AI 上下文有限，成员和 AI 都可能在陌生节点接手。

**决定**：

- `docs/STATUS.md` 是**唯一**进度快照，每次会话结束更新
- `docs/log/YYYY-MM-DD-<任务号>.md` 是**只增不改**的历史，一人一任务一个文件
- `docs/BACKLOG.md` 是任务真源，GitHub Issue 只是它的镜像
- 改代码的 PR 必须同时更新 STATUS 和新增一篇日志

**理由**：AI 和新成员只需读一页就能接手；历史放在日志里不会污染快照。

**代价**：每次提交多写十几行字。

**复审**：如果发现大家开始不更新，就改成 PR 模板强制勾选（当前已强制）。

## D-004 客户端框架：Electron（2026-11-03 · 已验证）

**背景**：需要 Windows 透明置顶窗 + 点击穿透 + 动画，且不能卡顿（73.08% 用户红线）。

**选项**：

| 方案 | 优势 | 劣势 |
|---|---|---|
| Electron | 纯 JS/TS，团队无 Rust 门槛；透明窗与点击穿透 API 成熟；Chromium 渲染稳定可预测 | 安装包大（~100MB+），空闲内存高 |
| Tauri | 包体小（~5MB），内存低 | 需要 Rust；依赖系统 WebView2，动画表现随机器差异大 |
| 其他（Qt / Flutter） | — | 团队学习成本更高 |

**决定**：**Electron 45.2.1**，P0-1 实测通过。

**实测数据（2026-11-03）**：

| 指标 | 结果 |
|---|---|
| 透明 + 置顶 + 穿透 | ✅ 全部可用 |
| 启动耗时 | 386–845 ms |
| 空闲内存 | 361 MB（4 进程） |
| 空闲 CPU（有动画） | 25.5% 单核 |
| 空闲 CPU（无动画） | 0.2% 单核 |

**理由**：

1. 红线是「卡顿」不是「内存」——实测证明 CPU 完全由**动画**决定（25.5% vs 0.2%），和框架无关
2. 团队无人会 Rust，Tauri 的隐性成本远超包体收益
3. 内存 361MB 偏高，但可通过动画节流与进程参数优化，且不触达红线

**代价**：安装包会到 100MB+，内存占用高于 Tauri。接受。

**复审条件**：若优化后空闲 CPU 仍 > 10% 单核，或打包体积 > 200MB，启动 Tauri 对照实验。

> 原定「CPU > 10% 就转 Tauri」的门槛**已调整**：实测发现 CPU 由动画驱动而非框架，换框架不解决动画开销，应先做节流。

## D-404 项目路径必须短且纯英文（2026-11-03 · 已定）

**背景**：项目原在 `E:\学习\人机交互与设计心理学\xinchong`，Electron 启动即崩（`0x80000003`，无报错）。

**决定**：项目路径固定为 **`E:\xinchong`**，禁止放到含中文或过深的路径。

**理由**：同一二进制在 101 字符中文路径下必崩，迁到 51 字符英文路径后正常。此外 `electron-builder` 打包、部分 npm 工具对中文路径也存在兼容问题。

**代价**：与课程文档不在同一目录，需要单独打开。

**复审**：无。

## D-006 形象来源：用户素材组装，不做 AI 生成（2026-11-03 · 已定）

**背景**：早期理解把 F5 当作「上传一张照片，AI 生成专属形象」。实际产品意图是：**用户按规格提供图片、视图、声音与性格等固定特性，程序组装成自己的专属桌宠。**

**选项**：

| 方案 | 问题 |
|---|---|
| A. AI 从照片生成角色 | 本地跑不动；云端跑违反隐私红线（53.85% 用户首要顾虑）；生成质量不可控 |
| B. 模板换色（早期设想） | 太浅，用户感受不到「这是我的角色」 |
| C. **用户素材组装** | 素材门槛高，需要配套规格与校验工具 |

**决定**：C。程序负责「导入、校验、播放、合成」，不负责「画」。

**理由**：把最不确定的生成环节移出项目范围，剩下的全是可控工程量。

**代价**：用户要准备素材，门槛上升。用三级梯度化解（L1 选现成 / L2 立绘+差分自动动画 / L3 完整序列帧）。

**复审**：若 L2 的使用率低于 L1，说明素材门槛仍然过高，需要补充「拍照一键生成」的替代路径。

## D-007 聊天：可选模块，用户自带 Key（2026-11-03 · 已定）

**背景**：用户希望保留聊天能力，但不希望产品被定义为聊天机器人。

**决定**：

1. **默认关闭**，用户主动在设置里填自己的 DeepSeek API Key 才启用
2. **没有 Key 时完全可用**，走本地固定话术库（按性格 × 场景挑句子）
3. Key 用 Electron safeStorage 加密存储，**只有主进程能读**，渲染进程拿不到
4. 任何失败（401 / 超时 / 额度用尽）都**回落固定话术**，宠物永远不"哑掉"
5. 只上传用户文本与性格设定，**不上传图片、音频、截图**

**理由**：这样既保留能力，又不承担 API 成本与数据合规责任，也守住了「不做聊天机器人」的定位。

**代价**：用户要自己去申请 Key，转化率会低。可接受——聊天本来就是增强项。

**复审**：若用户强烈要求在无 Key 情况下也有"像样"的对话，再评估内置免费额度。

## D-008 素材规格是产品契约（2026-11-03 · 已定）

**决定**：素材的格式、尺寸、命名、必需级别写入 docs/ARCHITECTURE.md 第 6 节，并同步产出面向用户的《素材规格说明书》（BACKLOG C4）与素材包模板 zip。

**理由**：没有明确规格，用户会反复来问「为什么导入失败」，团队会被答疑拖垮。

**代价**：规格一旦发布就不要随意改，改一次所有用户素材都得重做。
