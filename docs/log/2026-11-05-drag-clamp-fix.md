# 2026-11-05 · 拖拽到屏幕顶部会丢

## 现象

把宠物拖到屏幕最上方松手，窗口跑到 `y = -494`（窗口高 340，完全在屏幕外），宠物消失。
托盘「显示/隐藏」两次能拉回来。

报障机器：**1707×1067 @1.5x**（不是开发机的 125%）。

## 排查过程

### 先验证 clamp 的数学

```ts
minY = workArea.y - height + MIN_VISIBLE_PX
     = 0 - 340 + 60 = -280
```

按这个逻辑，`y` 最小只能到 -280。但实际是 -494 —— **说明 clamp 根本没执行**，
而不是算错了。

DPI 不一致的猜测可以排除：
`win.getBounds()` 和 `screen.workArea` 都是 DIP 单位，跨缩放是一致的。
如果是 DPI 问题，表现应该是「偏移量成比例误差」，而不是「完全不夹」。

### 真正的根因

拖拽的实现是：主进程每 16ms 读一次光标，把窗口设成「光标 - 按下时的偏移」。

拖到屏幕上边缘时，光标停在 `y=0`，而窗口要跑到 `y=-494`（因为抓取点在窗口下部）。
此时**光标已经不在窗口范围内**，松手时渲染层收不到 `mouseup`：

```
光标在窗口外松手 → 渲染层没有 mouseup → 不发 drag-end
                → 主进程的拖拽定时器永不停止
                → 每 16ms 继续把窗口设到 y=-494
```

`clampToVisibleArea` 只在 `drag-end` 里调用，而 `drag-end` 从来没到。

## 修复

### ① 拖拽过程中每帧夹位置（主进程）

新增 `clampPosition(x, y, w, h)`，拖拽循环里每帧调用。
**即使松手事件永久丢失，窗口也不可能被拖到完全看不见。**

### ② 渲染层用 `buttons` 兜底

```ts
if (dragging && event.buttons === 0) {
  endDrag();  // 早就松手了，只是没收到 mouseup
}
```

### ③ 抽出 `endDrag()`

`mouseup` 和兜底逻辑复用同一段收尾代码，避免遗漏。

## 验证（125% 缩放下）

| 场景 | 结果 |
|---|---|
| 抓宠物中部拖到 y=0 | 窗口停在 y=-331，可见 112px ✅ |
| **抓宠物底部拖到 y=0** | 窗口停在 **y=-370，可见 75px = 60 DIP** ✅ 精确命中下限 |

## 教训

**「事件丢失」是小窗口应用的系统性问题。**

窗口跟着光标跑，一旦光标跑到窗口外，渲染层就再也收不到这个鼠标事件。
凡是依赖「松手事件」来收尾的逻辑，都必须有**不依赖事件的兜底**：

- 主进程：每帧自我约束（夹位置）
- 渲染层：用 `buttons` 状态反推

同类风险还存在于：拖拽中途 Alt+Tab、拖拽时屏幕休眠。
