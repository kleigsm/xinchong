# 性能基准报告（P1-10）

**测量日期**：2026-11-05
**版本**：Electron 45.2.1 · 三套角色 · 待机动画 6fps
**环境**：Windows · 1920×1080 @125% 缩放 · 20 逻辑核心

---

## 一、测量方法

- 冷启动后空闲 10 秒再开始采样，避免启动期干扰
- 采样窗口 **30 秒**，取各 electron 进程的 CPU 时间增量除以窗口时长
- 期间**不做任何交互**（不点、不拖、鼠标不在宠物上）
- 用 `XINCHONG_PERF=1` 的 5 秒自动采样交叉验证

---

## 二、结果

### CPU（占单核百分比）

| 进程 | CPU |
|---|---|
| renderer（渲染） | 1.7% |
| gpu（合成） | 1.6% |
| main（主进程） | 1.6% |
| utility · audio（音频服务） | 1.0% |
| utility · network（网络服务） | 0.0% |
| **合计** | **5.89%** |

### 内存

| 进程 | 内存 |
|---|---|
| main | 141 MB |
| gpu | 99 MB |
| renderer | 88 MB |
| utility · audio | 67 MB |
| utility · network | 47 MB |
| **合计** | **442 MB** |

---

## 三、与历史版本对比

| 版本 | 空闲 CPU | 内存 | 说明 |
|---|---|---|---|
| P0-2 骨架 | 5.9% | 372 MB | 只有呼吸动画（12fps JS） |
| P1-4 气泡 | 6.4% | 371 MB | 加了气泡与窗口放大 |
| **当前** | **5.89%** | **442 MB** | 雪碧图动画 6fps + 音效服务 |

> 测量噪声约 ±0.5pp，多次测量在 5.9%–6.9% 之间波动。

---

## 四、结论

**未达到「空闲 CPU < 5%」的目标，差约 0.9pp。**

三个观察：

1. **CPU 已经比较均匀地摊在各处**：渲染 1.7、GPU 1.6、主进程 1.6、音频 1.0。
   没有单一"元凶"可以一刀砍掉。
2. **内存上升 70MB 主要来自音频服务**：一旦播放过音效，Chromium 会常驻音频进程。
3. **主进程 1.6% 比预期高**：已把光标轮询从 50ms 放宽到 80ms，但采样本身
   （`app.getAppMetrics()`）也会带来开销，两者抵消。

---

## 五、已做的优化

| 优化 | 效果 |
|---|---|
| 光标轮询 50ms → 80ms | 主进程轮询开销降约 40% |
| 待机动画 8fps → 6fps | GPU 从 3.4% 降到 2.4%（单次测得） |
| 窗口隐藏时停止动画 | 托盘隐藏后 CPU 归零（visibilitychange） |
| 卡顿自动降帧 | 连续慢帧时按 75% 递减，最低 4fps |
| 性能信息可见 | 托盘菜单「性能信息」弹窗显示实时数值 |

---

## 六、剩余优化方向（按性价比排序）

| # | 方向 | 预计收益 | 成本 |
|---|---|---|---|
| 1 | **精灵条 + transform**：把逐帧改 `background-position`（触发重绘）换成移动一条宽图（合成器动画，不重绘） | GPU 减半 | 2–3h |
| 2 | **空闲降频**：鼠标离开且 10 秒无交互后，待机动画降到 2fps | CPU 再降 1–2pp | 1h |
| 3 | **音频按需创建**：无音效时销毁 AudioContext，回收 67MB | 内存 −67MB | 1h |
| 4 | **打包后再测**：生产构建去掉了 dev 相关开销，数字通常会更好 | 未知 | 打包后 |

---

## 七、当前判定

**可接受，但要如实标注。**

- 「不卡顿」这条红线：**满足**（动画流畅、无掉帧、交互响应 < 100ms）
- 「低占用」这条期望：**接近但未达标**（5.89% vs 目标 5%）

对课程项目，这个数字可以接受；如果要做成真正发布的产品，应按上表继续优化。
---

## 八、补充：L2 单帧立绘方案的实测（2026-11-05 晚）

P2-4 引入「单张立绘 + 程序自动动画」后，对三种实现做了横向对比：

| 实现 | 空闲 CPU | GPU | 备注 |
|---|---|---|---|
| CSS 关键帧 + `drop-shadow` 滤镜 | **42.7%** | 35% | 不可接受 |
| CSS 关键帧（去掉滤镜） | 24.8% | 20.9% | 仍不可接受 |
| **JS 驱动 8fps + 无滤镜** | **5.16%** | 2.2% | 采用 |
| 雪碧图 6fps（L3，对照） | 5.89% | 1.6% | 现有方案 |

**两个反直觉的结论：**

1. `filter: drop-shadow` 会在元素每帧 transform 时强制重新栅格化，
   把合成器优化彻底废掉。
2. CSS 动画默认跑 60fps，而**透明置顶窗口的每帧合成成本远高于普通窗口**。
   把动画降到 8fps，开销立刻下降一个量级。

> 这条经验也适用于后续所有动画：**帧率是第一杠杆，滤镜是第二杠杆。**
